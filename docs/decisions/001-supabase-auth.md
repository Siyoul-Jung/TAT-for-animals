# 001 — Supabase Auth 기반 인증

## 결정
회원 인증을 **Supabase Auth**(이메일/비밀번호 + Magic Link)로 처리하고,
회원 데이터는 `profiles` 테이블에 저장한다.

## 배경
- 구독 서비스라 로그인 + 구독 상태(role) 관리가 필수.
- 시니어 사용자층이라 "비밀번호 없는 Magic Link" 로그인도 제공해야 함.
- 1인 개발이라 인증 서버를 직접 만들 여력이 없음.

## 대안
- **직접 인증 구현(JWT 발급 등)**: 보안 위험 + 구현·유지보수 비용 큼.
- **Auth0 등 별도 인증 서비스**: DB와 분리돼 통합 비용 발생.

## 이유
- Supabase가 인증 + DB(PostgreSQL) + 행 수준 보안(RLS)을 한 곳에서 제공.
- 가입 시 트리거로 `profiles` 행 자동 생성.
- 보호된 페이지는 미들웨어 → 서버 컴포넌트 → RLS 3단계로 접근 검증.

## 트레이드오프
- Supabase에 종속(vendor lock-in).
- RLS 정책을 정확히 설계해야 데이터 노출 위험을 막을 수 있음.
